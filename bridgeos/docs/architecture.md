# Appliance architecture

Buildroot 2026.02.2 external tree (`external.desc`, `Config.in`, `external.mk`) builds a musl/BusyBox initramfs and pinned Radxa 6.18.2 arm64 kernel. Upstream source-built boot firmware is a separate pinned input, not Buildroot's stock U-Boot package. `board/radxa-zero3-rt/post-image.sh` combines that firmware, kernel, ZERO 3W DTB, rootfs cpio and extlinux configuration into one raw SD image. GPT ext4 boot partition starts at 16 MiB; the identical firmware found in the supplied Debian ZERO 3E image occupies disk bytes from 32 KiB through roughly 9.6 MiB.

The kernel DTS describes independent DWC3 controllers: host for keyboard input and fixed peripheral for PC. ConfigFS provisions two HID functions (keyboard and vendor-defined). Both image profiles now embed the user-supplied USB identity `0xd86a:0x1000` in `/etc/bridge-gadget.conf`; ownership/assignment has not been independently verified. The previous unprovisioned production image exited gadget setup before binding the UDC. The new provisioned images still require a physical enumeration check.

The production process is intended to pin its receive/forward loop to CPU2 with SCHED_FIFO, prefault/lock memory, and keep blocking operations out of the hot loop. USB host IRQ CPU1 and gadget IRQ CPU3 are hypotheses; the startup policy resolves controller IRQs from `/proc/interrupts` and must fail/diagnose mismatches rather than blindly assign numeric IRQs. CPU0 handles housekeeping. Performance frequency and idle settings require runtime measurement before claiming an optimal configuration.

The debug profile adds kernel tracing, `rt-tests`, `trace-cmd` and `stress-ng` without adding them to production. It is an instrumented comparison, not an accepted p99.9 result. No source claims physical USB bus latency from userspace timestamps. Bare successful compilation cannot validate ZERO 3W port wiring, UDC enumeration or thermal state; that requires the actual board and host PC.
