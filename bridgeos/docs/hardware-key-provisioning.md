# RK3566 hardware-root commissioning (NOT YET PROVISIONED)

## What is stored where

The intended on-chip design places a per-device 16-byte root in RK3566 Secure OTP, reads it in source OP-TEE 4.9, derives a TA-UUID-bound subkey via `PTA_SYSTEM_DERIVE_TA_UNIQUE_KEY`, and derives the secp256k1 signing scalar in TA RAM. **This project has not provisioned such a root; the physical board's OTP state is unknown.** The TA exposes the Ethereum address and constrained session signatures, never the root or scalar to Linux. Under the user's stated boundary—trusted Secure World, no key access from Linux—this is the desired black-box signer; a separate silicon secp256k1 engine is not required.

The boundary is precise: OP-TEE core handles the OTP root, and the TA receives a derived subkey and holds the signing scalar. Replacing SD firmware with a malicious BL32 could export the root, so this design does **not** protect against an attacker who controls Secure World firmware. ROM-enforced authenticated boot and debug lockdown are needed for that stronger physical-attacker model; they are not a prerequisite for the narrower Linux-versus-TA property.

Only the unmodified Radxa ZERO 3W and RK3566 on-chip resources are in scope. No external secure element is assumed. The `hardware-root` release gate remains closed because no approved/provisioned RK3566 Secure OTP root slot or qualified Secure World entropy source has been verified for this project; it must not silently fall back to the known development key.

The current `optee-runtime` image uses the **public fixed development HUK and signing root**; it is not hardware-rooted. The existing `production` image has no BL32. The proposed `hardware-root` profile is blocked by both image and direct firmware build scripts; neither produces an on-chip-key identity. No script here writes OTP.

## Evidence and missing prerequisites

Pinned TF-A RK3568 `plat/rockchip/rk3568/drivers/otp/otp.h` defines 448 secure halfwords (896 bytes), 64 nonsecure halfwords, and a halfword-read interface. Its `otp.c` uses secure SBPI reads, with no programming implementation. The source OP-TEE port mirrors this read sequence. **Neither source proves which secure bytes are free for customer HUK, how to program or read-lock them, or whether this board has already used those cells.** The `secure_otp_huk_byte_offset` is deliberately not guessed; build rejects absent/unaligned/out-of-range offsets. A board-specific Rockchip OTP/fuse allocation document and independently reviewed factory programming/lock procedure are required. Do not experiment by burning the user's board. Check whether ROM/boot firmware consumes a candidate slot before any programming.

The pinned `rkbin/doc/release/RK3568_EN.md` for vendor BL32 v2.14 mentions an OTP hardware lock and a key-reader access lock. TF-A's `otp.h` defines `REG_KEY_READER_CONFIG`, but its RK3568 implementation does not exercise that register: it reads raw halfwords into software memory. Neither release note nor source specifies a write-only customer key slot, proves secure key-reader-only derivation on **RK3566**, or documents a silicon secp256k1 signing engine. A register name or opaque BL32 string is not a verified non-exportable key primitive.

The pinned vendor BL32 also contains the strings `rk_user_ta_oem_otp_key_hmac`, `rk_otp_read_oem_otp_key` and `Not support write oem huk!`. These are evidence of compiled API names and a negative path, **not** proof that this specific RK3566 has a usable customer key slot or on-chip ECDSA engine. A hardware HMAC returning a 32-byte derived signing scalar to TA RAM would still let replacement BL32 export that scalar; the silicon primitive must perform secp256k1 signing internally for the literal strongest guarantee.

[Rockchip OTP Developer's Guide v1.4.0, §3.1](https://raw.githubusercontent.com/DeciHD/rockchip_docs/main/rv1103_rv1106/RV1106_EN/security/Rockchip_Developer_Guide_OTP_EN.pdf#page=7) explicitly lists a **224-byte Protected OEM Zone on RK3566/RK3568**, accessible to trusted TAs but not directly to Normal World. Its vendor secure-TA interface uses *relative* offsets (commands 160 for size, 130 for read), not the physical byte offset expected by this project's source OP-TEE HUK reader. The guide marks **write lock unsupported** for RK3566/RK3568; the [OEM cipher key table](https://raw.githubusercontent.com/DeciHD/rockchip_docs/main/rv1103_rv1106/RV1106_EN/security/Rockchip_Developer_Guide_OTP_EN.pdf#page=16) offers four 16/24/32-byte key IDs but marks hardware-read support absent on these SoCs. This establishes a possible **TA-only** root-key location, not a safe raw offset, already-programmed key, or verified one-time factory writer for this image. The separate 64-byte Non-Protected OEM zone is readable by Linux and must never hold the root.

**Hardware build blocker reproduced:** OP-TEE 4.9 with `CFG_INSECURE=n` cannot link on this RK3566 port: `undefined reference to plat_rng_init`. The development build masks this by enabling OP-TEE's insecure RNG. The RK356x Linux device tree says the RK3566 HWRNG at `0xfe388000` has *unacceptably low quality random data* and disables it. Do not replace the missing driver with a stub, a fixed seed or that nonsecure HWRNG without qualification. A reviewed Secure World entropy source with startup health tests is required before building/deploying the hardware-root image. An OTP HUK cannot replace runtime entropy for OP-TEE's storage and key operations.

[Rockchip RK3566 datasheet §1.2.6](https://raw.githubusercontent.com/DeciHD/rockchip_docs/main/rk3566_rk3568_rk3568j/Rockchip_RK3566_Datasheet_V1.1.pdf#page=10) lists Secure OTP and a 256-bit TRNG. [RK3568 TRM Part1 Table 1-1 and SCRU §2.5](https://raw.githubusercontent.com/DeciHD/rockchip_docs/main/rk3566_rk3568_rk3568j/Rockchip_RK3568_TRM_Part1_V1.3-20220930P.PDF#page=150) map candidate Secure TRNG `0xfe370000`, secure clock gates SCRU+`0x180` bits 7:6, and reset SCRU+`0x208` bits 11:10. [RK3568 TRM Part2 chapter 5](https://raw.githubusercontent.com/DeciHD/rockchip_docs/main/rk3566_rk3568_rk3568j/Rockchip%20RK3568%20TRM%20Part2%20V1.1-20210301.pdf#page=224) describes its register controls and output but gives no entropy estimate or documented health flags; its §5.3.1 mistakenly names `RST_CTL` for the self-clearing start bit, while §5.4.2 names `RNG_CTL`. This is a source-backed **RK3568 layout hypothesis on RK3566**, not a qualified secure RNG. The pinned vendor BL32 uses sample count 1079/speed 1; Linux uses 1000/speed 0 for a different nonsecure block, disabled on RK3566 for low quality.

Read-only reverse analysis: pinned Rockchip BL32 v2.16 (SHA-256 `69cf1dc21ac0bd1e4a4eec93ee35eea204f117b2168591226c0d112983e06992`) limits Protected OEM *relative* offsets to `0xE0` bytes and adds physical byte offset **`0x2A0`** on both the read (`0x08421858–0x084218AC`) and write (`0x08421928–0x084219A0`) paths. Its size command returns `0xE0` (`0x08421A4C–0x08421A5C`), and the resulting `0x2A0–0x37F` range ends at TF-A's 896-byte Secure OTP boundary. This mapping justifies the separate **read-only** `otp-lab` probe of bytes `0x2A0–0x2AF`, not a source-verified writer, HUK identity, or permission to burn; the rest of the 224-byte zone has not been inventoried on the user's board.

[Rockchip RK3568 TRM Part1 §2.4, CRU_SOFTRST_CON28](https://raw.githubusercontent.com/DeciHD/rockchip_docs/main/rk3566_rk3568_rk3568j/Rockchip_RK3568_TRM_Part1_V1.3-20220930P.PDF#page=146) lists the OTP PHY reset at CRU+`0x470`, bit 15. Pinned TF-A `soc.h` and this project's original dormant HUK reader used `CRU_SOFTRST_CON0=0x300`, which targets gate `0x370` for index 28. The source OP-TEE patch now uses `0x400` (reset index 28 = `0x470`) and ECC-enabled Protected OEM reads. The isolated OTP lab has verified **blank** board reads with this register path; the HUK backend remains blocked until a qualified root is safely provisioned and read back, not merely because the register could be read.

`./scripts/build.sh otp-lab` produces an **unsigned, read-only, no-signer** SD image at `output-otp-lab/images/radxa-zero3-rt.img` (never overwrite the known-good SD). On an unfused recoverable ZERO 3W, no OTG/HID enumeration is expected. After at least ~90 seconds, power down and inspect `RTDIAG/STATUS.TXT` on the Mac; report only `otp_lab_status`, `oem_key_slots`, `last`, `live` and whether Linux booted—**never publish raw OTP bytes**. For `otp_lab_status`, `0x4F545001` = entered but unfinished; `...02` = read failure; `...03` = inconsistent reads; `...04` = first Protected OEM 16 bytes read zero twice; `...05` = nonzero, not a HUK attestation. An empty RTDIAG means diagnostics did not complete. No status authorizes an irreversible OTP write. Restore the working card after testing.

The rebuilt `otp-lab` image also checks four *different* 32-byte OEM cipher-key slots at raw Secure OTP `0x200`, `0x220`, `0x240`, `0x260` inside Secure World (vendor `rk_otp_oem_otp_key_is_written` computes `0x200 + key_id * 0x20`). Each slot is read twice; only a four-bit presence mask is published as `oem_key_slots` in `STATUS.TXT`: `0x4B455900` = all four read zero, bits 0–3 of the final byte identify nonzero slots, `...FE` = inconsistent reads, `...FF` = read error. A nonzero slot does **not** prove its provenance, uniqueness or suitability as a sealing root. The preceding uploaded `otp_lab_status=0x4F545004` came from the **earlier image**, so it says nothing about these four slots. The new image still has no OTP write code, signer TA or private-key bytes.

The user's uploaded `otp-lab` `STATUS.TXT` reports `otp_lab_status=0x4F545004` and `Linux zero3-otp-lab 6.18.2`; `DMESG.TXT` reports `optee: revision 4.9 ... initialized driver`. On this **one observed boot**, source Secure World ECC reads of physical bytes `0x2A0–0x2AF` succeeded twice and both returned all zero; this is a confirmed blank **candidate** on that board at that time, not evidence of a programmed HUK, qualified entropy, write endurance, or stability across cold boots. `OPTEE.TXT` confirms `not-installed-no-signer-TA`. No OTP was written.

The subsequent uploaded `otp-lab` image reports **both** `otp_lab_status=0x4F545004` and `oem_key_slots=0x4B455900`; Linux again initialized source OP-TEE 4.9. On that board all four 32-byte OEM KEY0–KEY3 slots and the first 16 Protected OEM bytes read zero consistently within the probe. This rules out using those documented OEM slots as an already-provisioned HUK for persistent TA storage; it does not rule out undocumented ROM-only silicon secrets. No write or key import occurred.

The vendor BL32's **programming** body (`0x0840E0D8–0x0840E5DC`) uses a multi-stage SBPI sequence, including OTP PHY control and commands `0xF0`, `0xFB`, `0xC0`, `0xFF`, `0x01`, `0x02`. The pinned open TF-A driver implements reads only, and the public RK3568 TRM does not specify those programming phases or the required voltage/lock/readback conditions. Reconstructing instructions from opaque firmware is enough to locate the OEM range for a **read-only** preflight, but not a safe basis to burn a customer's irreplaceable board. This project keeps the source-only firmware and does not transplant the vendor BL32 or expose a write command.

The `rng-lab` profile builds a separate **no-key, no-OTP** OP-TEE observer using only the documented secure TRNG/SCRU controls. It writes a status marker to PMUGRF OS_REG9 (`0xfdc20224`), never seeds OP-TEE's RNG, and includes no bridge daemon, signer TA or SRS. On a spare SD and unfused recoverable board, `rng_lab_status=0x54524e05` in `RTDIAG/STATUS.TXT` means only that the start bit cleared and eight **unqualified** DOUT words were observed; `...02/03/04` identify mapping/reset/start failures. No result qualifies entropy. An empty RTDIAG means diagnostics did not complete, not necessarily that Linux never ran. No OTP or fuse write occurs.

The user's `rng-lab` SD report showed `rng_lab_status=0x54524E05`, Linux `6.18.2 PREEMPT_RT`, and `optee: revision 4.9 ... initialized driver`. This proves the observer reached the documented control path on the user's ZERO 3W; it does **not** measure output entropy. `random: crng init done` in Linux dmesg is a separate Linux RNG event, not Secure World quality evidence. That flashed image's `OPTEE.TXT` says `skipped-active-bridge-owns-TA`, an old diagnostic label error: no signer TA or bridge is installed in the lab image; future debug images use `not-installed-no-signer-TA`.

Because `rng-lab` removes `S99bridge`, the Mac should **not** see any OTG/HID gadget. `STATUS.TXT` is a one-time file written only after Linux reaches `S99zzdiag start` and its 60-second delay, then sync/unmount; wait at least ~90 seconds after power-on before removing the spare SD. If `RTDIAG` remains empty, the system did not complete diagnostics; use a UART boot log to distinguish BL32, kernel, init and FAT-mount failures.

A secure OTP HUK alone does **not** make signatures authentic: this SD-boot appliance currently lacks an enforced authenticated boot chain. An attacker able to replace BL32 can read OTP via modified Secure World firmware. Authenticate ROM→SPL→BL31/BL32→U-Boot→kernel/TA or constrain physical media access before claiming a non-exportable identity. Source OP-TEE's `/run/tee` is volatile: it boots development TA rollback storage but does not provide anti-rollback. Commission RPMB or another authenticated persistent rollback store separately. Linux still supplies events and timestamps to the TA, so a secure key cannot independently attest physical key origin.

Boot-chain evidence: in generated `sources/boot-firmware/out-optee-dev/u-boot.itb`, `fdtget -l ... /images/op-tee` shows an image `hash` child, but `fdtget -l ... /configurations/config-1` shows **no signature child**. A hash on removable media is not authentication. `CONFIG_SPL_FIT_SIGNATURE=y` in Radxa's U-Boot defconfig is capability, not an installed trust anchor or mandatory signature policy. `board/radxa-zero3-rt/post-image.sh` loads an unsigned `/boot/Image`, DTB and initramfs via extlinux. Pinned `rkbin/tools/fit-sign.sh` supports a signed-loader/FIT workflow using opaque `rk_sign_tool`, but its `--burn-key-hash` flag sets an SPL DTB property associated with irreversible key-hash enrollment; it does not establish that ROM keys/fuses are enrolled on this board. No trusted ROM status measurement or authenticated update/recovery path exists here. Until a full signed chain is built and physically fuse-verified, alternate SD firmware can export this port's software-readable OTP secret.

Offline proof of **one** stage only (no fuse writes, no flashable artifact): with a temporary RSA-2048 key outside the checkout, pinned `rk_sign_tool` accepted `cc --chip 3566`, `lk --key/--pubkey`, `sb --idb` on this project's 202,752-byte `idbloader.img`, and `vb --idb` succeeded. Re-loading a different public key or flipping an idblock byte made verification fail. That idblock is byte-identical to the prefix of `u-boot-rockchip.bin`. This proves offline signing/verification of the loader *format*, not BootROM fuse enforcement or authentication of BL32/Linux. The test keys and modified idblock were deleted.

Reproduce the safe offline signing and wrong-key/tamper checks with `python3 tests/test_idblock_signature.py`. This test uses ephemeral test keys and deletes them; **it never signs the deployable firmware, touches a board, or changes fuses**.

Candidate authenticated-boot sequence (not deployed): Rockchip ROM must verify a signed idblock/TPL/SPL against a **fused** production public-key hash; that SPL must require a signed FIT configuration covering BL31, BL32, U-Boot and board DTB with its verification key in ROM-authenticated SPL; U-Boot must boot only a signed kernel FIT covering `Image`, ZERO 3W DTB, initramfs and boot arguments with a key in that signed U-Boot image. Current extlinux/raw `Image` boot must be removed, and recovery/USB-download paths and debug access must not permit arbitrary BL32. `rkbin/tools/fit-sign.sh` and U-Boot binman `fit,sign` supply signing capabilities, **not proof** that ROM fuses, SPL-required-key policy or a signed Linux boot path are active. Never use the Rockchip `--burn-key-hash` option as a routine build step; fuse enrollment is a separate irreversible operation requiring board-specific recovery validation.

`./scripts/build.sh signed-lab` exercises that signed idblock→SPL FIT→signed kernel FIT packaging with an external **laboratory boot key** and the known-public development HUK, without touching OTP or fuses. It has a fixed SD-card (`mmc 1:1`) signed `/boot/kernel.itb` handoff and a macOS-readable RTDIAG partition. Booting this image on an unfused board tests compatibility, **not ROM signature enforcement or production key non-exportability**. The `hardware-root` builder remains closed until fuse state, entropy, OTP slot, debug lock and recovery policies are proven separately.

The signed-lab build publishes `output-signed-lab/images/boot-key-identity.json`: it checks that SPL and U-Boot proper contain the same RSA-2048 public key with `required=conf` and records SHA-256 of the **raw public modulus only**. It is **not** a Rockchip ROM fuse value. On the signed mainline binman idblock, pinned `rk_sign_tool otp --loader ... --hash` returned `failed to init rkboot object` (exit 251), although `sb`/`vb` accepted that idblock. Do not infer or burn a fuse payload from this fingerprint; obtain the documented RK3566 ROM enrollment format and readback procedure before any irreversible operation.

OP-TEE 4.9 contains a `PTA_RK_SECURE_BOOT_GET_INFO`/`BURN_HASH`/`LOCKDOWN_DEVICE` API, but `core/arch/arm/plat-rockchip/conf.mk` enables it only for **rk3588**. Its `core/drivers/rockchip_otp.c` programs an RK3588-style `OTP_S_AUTO_CTRL` register and the platform constants `ROCKCHIP_OTP_RSA_HASH_INDEX` are under the RK3588 branch. RK3566's pinned TF-A instead uses secure SBPI halfword reads. Calling or transplanting the RK3588 fuse writer on ZERO 3W is unsafe; no RK3566-compatible read-only fuse status or write/lock implementation is established.

The current TA validates the header policy/bitstream and an SRS availability flag, but it does **not** independently recompute the Linux-loaded SRS bank hash: the host-side build preflight only pins the packaged bank. Authenticated boot and a TA-side SRS binding must be reviewed before treating its commitment as a secure attestation.

## Separately reviewed factory procedure (no programming automation here)

1. Inventory the exact board/SoC revision and recovery path. Use `otp-lab` on a spare SD to verify **on that board** that candidate Protected OEM bytes `0x2A0–0x2AF` read as zero consistently across two cold boots. A nonzero or read-error result is a stop condition, not an invitation to scan/write adjacent cells. Rockchip's guide says **RK3566 Protected OEM write lock is not supported**; do not invent lock bits. Require explicit, board-specific human approval of the irreversible 16-byte target after the source-only programming sequence and readback behavior have been independently reviewed and tested on an expendable unit.
2. Only after Secure World entropy is qualified, generate the 128-bit root inside Secure World on this RK3566. A separately reviewed factory-only provisioner must verify the exact blank slot again, program it once, read it back *internally*, erase working copies, and export only the public Ethereum address. Neither root nor derived scalar may traverse Linux, USB, SD/eMMC, the build host or logs. **No such source-verified writer or qualified generator exists here today; no OTP write has been performed.** Authenticated ROM boot and debug lock are distinct, stronger physical-attack defenses; their absence must be disclosed rather than falsely folded into the narrower Linux-versus-TA claim.
3. Provision a product TA trust key outside this repository, provide **only its public key** to OP-TEE core, sign the constrained TA offline, and remove the signing key from ordinary developer systems. The current build accepts an external private PEM on an isolated build host; integrating an HSM/offline signing ceremony is required for final factory operation.
4. Approve the exact BN254 G1 bank (exactly 200,000 contiguous points, 64-byte BE x/y each), corresponding prover SRS/G2 ID and firmware identity. Approve the bitstream hash. Set up authenticated persistent OP-TEE storage and enforce signed boot before registering any device on chain.
5. Build the `hardware-root` profile with an external review record (below), flash through Etcher, and call Vendor HID GET_INFO twice across cold power cycles. Require identical address on the **same unit**, distinct address on another unit, the approved SRS/bitstream hashes, `max_events=50000`, and a successful SET_HEADER→START→STOP→GET_RESULT signature recovery against that address. Never equate a GET_INFO response alone with OTP read security. Capture no secret bytes in this check.

### Build-only external record

`OSUMANIA_PROVISIONING_RECORD` is an **out-of-tree** JSON object with `board` (`radxa-zero-3w-rk3566`), `device_serial`, `otp_slot_reference`, `approved_secure_otp_slot`, `secure_otp_huk_byte_offset` (even byte offset 0–880), `srs_bank` (absolute path), `srs_sha256` (64 hex), `ta_sign_key` (external private PEM), `ta_public_key` (matching public PEM), and `ta_key_reviewed`. It contains **no HUK or device signing scalar**. At each build preflight a 32-byte public `build_marker` is deterministically derived from `sources.lock`, the approved bank hash, product TA public key, OTP byte offset and board serial, then compiled into the legacy `bitstream_hash` protocol field. Identical reviewed inputs reproduce the same marker; changing any of them changes the marker. **Without an actual FPGA bitstream this is a release identifier, not hardware bitstream attestation.** The marker is emitted in preflight JSON for registration. Boolean review fields are operator attestations; keep the record and TA trust private key outside the checkout.

The following are **future commissioning commands**, not an executable recipe on the current board: `build.sh hardware-root` deliberately refuses to emit an image until ROM secure-boot enforcement, authenticated BL32, debug-port lock, secure RNG and OTP allocation have concrete verification paths.

```sh
OSUMANIA_PROVISIONING_RECORD=/secure/factory/zero3w-serial.json ./scripts/build.sh hardware-root
./scripts/verify.sh output-hardware-root hardware-root
python3 tools/macos-vendor-hid-get-info.py
python3 tools/macos-vendor-hid-signing-test.py --capture-seconds 8 --min-events 4 \
    --srs /secure/approved/srs-g1-be.bin --srs-sha256 "$APPROVED_SRS_SHA256"
```

`APPROVED_SRS_SHA256` must come from an independently approved SRS manifest, **not** be computed from the untrusted bank being checked.

## Off-host validation on a separate macOS computer

This repository does not have the user's ZERO 3W attached. After a separately authorized factory OTP operation and authenticated-boot validation, transfer **only the image and public expected address/hash**, never the HUK or a device signing key, to the Mac. Check `shasum -a 256 radxa-zero3-rt.img` against the build manifest, flash with Etcher, and run `python3 tools/macos-vendor-hid-get-info.py --json`. Power off fully and repeat; the address must remain identical across cold boots and differ from the public development address `0xf15e068b7a61cc36391fab39512fd9e6f9c9e8f0` and another commissioned board. Run `python3 tools/macos-vendor-hid-signing-test.py --capture-seconds 8 --min-events 4`; its recovered signer must match GET_INFO. No secret readback through USB is permitted. **Vendor HID results alone cannot certify OTP read locks, debug-port disablement or ROM secure-boot fuses**: verify these separately with a trusted factory test before declaring the key non-exportable.

The preflight checks offset alignment/range, bank length/hash, bitstream identifier, external TA private/public key pair and absence of development backend. This is a **build gate**, not a substitute for approved OTP allocation, secure boot, read-lock checks, on-board identity tests or latency measurements. If any prerequisite is missing, use the development profile for laboratory functionality; do not register its publicly derived address as a production hardware identity.
