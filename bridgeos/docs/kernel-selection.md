# Kernel selection and RT configuration

Use Radxa [`linux-6.18.2`](https://github.com/radxa/kernel/tree/559f4f921a01e5358602153364c618fe2a3e431e), **commit `559f4f921a01e5358602153364c618fe2a3e431e`** (not a moving branch head), with `arch/arm64/configs/defconfig` as the starting configuration. Merge `board/radxa-zero3-rt/kernel.fragment` after that defconfig; `kernel-debug.fragment` is separate. The custom `rk3566-radxa-zero-3w-rt.dtb` comes from `board/radxa-zero3-rt/dts/rockchip/rk3566-radxa-zero-3w-rt.dts` through Buildroot's `BR2_LINUX_KERNEL_CUSTOM_DTS_DIR`. Keeping the source in the `rockchip/` directory is necessary for 6.18 arm64 DT build targets. It includes the pinned tree's `rk3566-radxa-zero-3w.dts`; do not use the older 6.1 `*-ap6212.dts` with this branch.

Why not the newer-dated 6.1 vendor branch? Radxa [`linux-6.1-stan-rkr5.1` at `f87fca6cefcb6229c7f81399dd351cf658940bfa`](https://github.com/radxa/kernel/tree/f87fca6cefcb6229c7f81399dd351cf658940bfa) has the necessary PREEMPT_RT menu entry in [`kernel/Kconfig.preempt`](https://github.com/radxa/kernel/blob/f87fca6cefcb6229c7f81399dd351cf658940bfa/kernel/Kconfig.preempt), but that entry depends on `ARCH_SUPPORTS_RT`, which its [`arch/arm64/Kconfig`](https://github.com/radxa/kernel/blob/f87fca6cefcb6229c7f81399dd351cf658940bfa/arch/arm64/Kconfig) does not select. Its `rockchip_linux_defconfig` selects `PREEMPT_VOLUNTARY`. A fragment setting `CONFIG_PREEMPT_RT=y` against that branch would silently fall back after `olddefconfig`; simply toggling the architecture gate is not a real 6.1 RT backport. The selected 6.18.2 [`arch/arm64/Kconfig`](https://github.com/radxa/kernel/blob/559f4f921a01e5358602153364c618fe2a3e431e/arch/arm64/Kconfig) selects `ARCH_SUPPORTS_RT`, and its [`kernel/Kconfig.preempt`](https://github.com/radxa/kernel/blob/559f4f921a01e5358602153364c618fe2a3e431e/kernel/Kconfig.preempt) permits `PREEMPT_RT` when `EXPERT=y` and `COMPILE_TEST=n`. Its [`defconfig`](https://github.com/radxa/kernel/blob/559f4f921a01e5358602153364c618fe2a3e431e/arch/arm64/configs/defconfig) starts from `PREEMPT=y`, `USB_DWC3=y`, `USB_GADGET=y`, `USB_XHCI_HCD=y`, and `USB_CONFIGFS=m`.

The production fragment changes the preemption choice to `EXPERT=y`, `PREEMPT_RT=y`, `PREEMPT_DYNAMIC=n`. It makes `USB_CONFIGFS=y`, `USB_CONFIGFS_F_HID=y`, `USB_DWC3_DUAL_ROLE=y`, `USB_XHCI_HCD=y`, `PHY_ROCKCHIP_INNO_USB2=y`, and `PHY_ROCKCHIP_NANENG_COMBO_PHY=y`, allowing the DWC3 core to drive the fixed device port and the separate host port without relying on a loadable combo PHY. `HID=y`, `USB_HID=y`, `HIDRAW=y`, `INPUT_EVDEV=y` serve the actual host-side inputs. These are symbols in the pinned [DWC3](https://github.com/radxa/kernel/blob/559f4f921a01e5358602153364c618fe2a3e431e/drivers/usb/dwc3/Kconfig), [gadget](https://github.com/radxa/kernel/blob/559f4f921a01e5358602153364c618fe2a3e431e/drivers/usb/gadget/Kconfig), and [HID](https://github.com/radxa/kernel/blob/559f4f921a01e5358602153364c618fe2a3e431e/drivers/hid/Kconfig) Kconfigs, not inferred knobs. `CONFIGFS_FS` is selected by `USB_LIBCOMPOSITE`. The debug fragment enables lockdep/preempt checks and latency/function tracers, whose overhead invalidates production latency measurements.
`PHY_ROCKCHIP_INNO_USB2` also depends on `EXTCON`, explicitly kept built in so the PHY's connector events are available without module loading.

For the headless USB appliance, the production fragment disables `WLAN`, `BT`, `MEDIA_SUPPORT`, `DRM`, and `SOUND`/`SND`; the Linux DTB also disables onboard Wi-Fi SDIO1, its power-sequence node, and Bluetooth UART1. The SD card (`sdmmc0`), optional eMMC (`sdhci`), UART2 serial console, storage/USB host stack, `PRINTK`, network core, and other broad arm64 defconfig drivers remain for first-board boot and recovery. HDMI output is intentionally unavailable with `DRM=n`; further defconfig pruning should wait for a successful physical boot and an explicit dependency inventory, rather than risk removing boot-critical PHY, MMC, regulator, clock, or console support.

`ROCKCHIP_THERMAL=y` is built in so thermal throttling can be observed without module loading. `DEBUG_FS=n` in production; the debug profile explicitly re-enables it for controlled tracing. These do not imply a measured thermal or latency result.

The pinned [ARM64 Kconfig](https://github.com/radxa/kernel/blob/559f4f921a01e5358602153364c618fe2a3e431e/arch/arm64/Kconfig) forces `SMP=y`; the base defconfig has `HIGH_RES_TIMERS=y` and `IRQ_TIME_ACCOUNTING=y`. Production pins high-resolution timers, `HZ_1000=y` (1 ms jiffies, with potential periodic-tick overhead), and `CPU_ISOLATION=y` (capability only; no CPU is isolated without affinity/pinning). The generated production `.config` **retains `IRQ_TIME_ACCOUNTING=y` from the baseline**; measure its cost before changing it. `RCU_NOCB_CPU` and `nohz_full` are not enabled: callback offload and full-tick isolation require a hardware-backed comparison for this syscall/IRQ-heavy workload. See [HZ choice](https://github.com/radxa/kernel/blob/559f4f921a01e5358602153364c618fe2a3e431e/kernel/Kconfig.hz), [isolation and IRQ accounting](https://github.com/radxa/kernel/blob/559f4f921a01e5358602153364c618fe2a3e431e/init/Kconfig), and [RCU offload prerequisites](https://github.com/radxa/kernel/blob/559f4f921a01e5358602153364c618fe2a3e431e/kernel/rcu/Kconfig).

**Boot caveat:** mainline U-Boot/TF-A firmware carries its own FIT board DTB, not the Linux DTB. Extlinux must load the built 6.18 `Image` and `rk3566-radxa-zero-3w-rt.dtb` together; U-Boot's firmware DTB does not contain the Linux peripheral-role override. The user reports boot from an earlier image, but its unprovisioned gadget never bound the UDC. Both profile configurations now include user-supplied `0xd86a:0x1000`; actual PC enumeration, negotiated speeds and worst-case RT latency remain unmeasured. The built `.config` contains `CONFIG_PREEMPT_RT=y`; that does not prove any timing target.
