# ZERO 3W host and gadget ports

Radxa's [ZERO 3W product specification](https://www.radxa.com/products/zeros/zero3w/) distinguishes the **USB 3.0 HOST Type-C** port for data from the **USB 2.0 OTG Type-C** port for power and data. They are different physical connectors. This image assigns the USB 3.0 Type-C connector to attach real USB HID devices, and the USB 2.0 OTG/power Type-C connector to appear to a separate computer as a USB HID gadget. The USB 2.0 gadget path is **high-speed at most**, not SuperSpeed, even though its controller is named DWC3.

In the pinned [Radxa 6.18.2 ZERO 3W board DTS](https://github.com/radxa/kernel/blob/559f4f921a01e5358602153364c618fe2a3e431e/arch/arm64/boot/dts/rockchip/rk3566-radxa-zero-3w.dts), [`rk3566-radxa-zero-3.dtsi`](https://github.com/radxa/kernel/blob/559f4f921a01e5358602153364c618fe2a3e431e/arch/arm64/boot/dts/rockchip/rk3566-radxa-zero-3.dtsi) enables both `usb_host0_xhci` and `usb_host1_xhci`, plus `usb2phy0` and both of its ports. The [RK3566 base](https://github.com/radxa/kernel/blob/559f4f921a01e5358602153364c618fe2a3e431e/arch/arm64/boot/dts/rockchip/rk3566-base.dtsi) attaches `usb_host0_xhci` to `usb2phy0_otg`, marks its maximum speed `high-speed`, and gives it the USB2 PHY extcon. The [RK356x base](https://github.com/radxa/kernel/blob/559f4f921a01e5358602153364c618fe2a3e431e/arch/arm64/boot/dts/rockchip/rk356x-base.dtsi) locates that DWC3 at `0xfcc00000`, initially `dr_mode = "otg"`; it locates a separate DWC3 `usb_host1_xhci` at `0xfd000000`, with `dr_mode = "host"`, `usb2phy0_host`, and `combphy1` USB3 PHY. The external `rk3566-radxa-zero-3w-rt.dts` includes the original board DTS and overrides **only** `&usb_host0_xhci` to `dr_mode = "peripheral"`. Leave the other controller and the PHY/clock assignments untouched; do not turn the host connector into a gadget or assign both functions to one DWC3.

```
USB 3.0 HOST Type-C  -> DWC3 @ fd000000 -> usb2phy0_host + combphy1 -> USB HID input
USB 2.0 OTG/power C  -> DWC3 @ fcc00000 -> usb2phy0_otg          -> ConfigFS HID gadget
```

The kernel needs built-in XHCI, DWC3 dual-role support (one controller is still host), RK3568 USB2/combo PHYs, USB gadget ConfigFS HID, and the host USB HID + evdev/hidraw stacks; see `kernel.fragment`. A runtime process must create **both** the keyboard and vendor HID ConfigFS functions and bind the composition to the UDC; device tree alone does not advertise any HID interface. On first hardware bring-up, confirm `/sys/class/udc/` contains the device controller, that the host-side `lsusb` shows attached inputs, and that the other computer enumerates the two intended HID interfaces after binding. The USB-C OTG connector is also the board's power input: provide a valid power source/host connection and respect the board's power budget. The Linux 6.18 board tree does not explicitly describe a USB-C connector/Type-C policy controller, so successful Type-C attach and board powering must be checked on the real unit; neither DTS compilation nor a populated UDC proves them. Wireless chip variations (the older 6.1 branch has separate `ap6212` and `aic8800ds2` DTS files) are unrelated to the USB path and are not promised by this generic upstream-style 6.18 board DTS.

Both image profiles carry the user-supplied `0xd86a:0x1000` identity; assignment was not independently verified. An empty `/sys/class/udc` means controller/PHY/role or power failure, whereas a present UDC with an empty ConfigFS `bridgeos/UDC` means gadget setup/bind failed. The Type-C cable must support data and connect to the **USB 2.0 OTG/power** port, not the USB 3.0 host port. UART is optional, not a prerequisite for the debug procedure below.

An earlier initramfs wrote `/proc/sys/kernel/hotplug` despite `CONFIG_UEVENT_HELPER=n`; `set -e` aborted `/init` before ConfigFS. The corrected image removes that path. On macOS **System Information → USB**, first look for VID `d86a`, PID `1000`, then the two HID interfaces. Absence from the USB tree means no physical enumeration, not a keyboard keymap failure. HID enumeration of the corrected image remains unobserved here.

## UART-free diagnosis on macOS

`./scripts/build.sh debug` creates a 125,849,600-byte image with an 8 MiB GPT Basic Data/FAT volume labelled `RTDIAG`; production has no writable diagnostic partition. This debug build now uses the **same kernel-default HID polling interval as production**, so it can diagnose the reported failure at both intervals without changing transport behavior. Flash `output-debug/images/radxa-zero3-rt.img`, connect the Mac to the USB 2.0 OTG/power port with a data-capable cable, repeatedly press/release keys during the first minute, then wait at least 90 seconds after power-on before shutting down and reinserting the SD card into the Mac. Inspect `RTDIAG/STARTUP.TXT` (daemon and keyboard discovery), `STATUS.TXT` (UDC/HID/daemon process), `COUNTERS.TXT` (successful gadget writes and drops), and `DMESG.TXT`. This is one post-activity snapshot, not periodic logging. Empty FAT means the snapshot service did not write; it does not prove which earlier boot step failed.

Interpret counters: no `keyboard source:` in `STARTUP.TXT` and zero reports indicates keyboard discovery/evdev; selected keyboard but `keyboard_reports=0` despite physical activity indicates read/translation/wakeup; reports incrementing with no macOS key events indicates HID queue versus host interpretation. `keyboard_dropped` or a censored histogram tail means backpressure; neither zero reports nor successful userspace `write()` proves physical USB delivery. No captured trace yet establishes the specific root cause of the interval=1 regression.

Interpret `STATUS.TXT`: no listed UDC → DWC3/USB2 PHY probing or power; UDC present but no `UDC=` binding → inspect `STARTUP.TXT` for ConfigFS errors; UDC bound but `state` not `configured` → Type-C attach/VBUS/cable/power path. The Debian ZERO 3E reference DTB leaves `usb@fcc00000` in `dr_mode=otg`, while this appliance forces `peripheral`; this is a **hypothesis to test after the snapshot**, not proof that fixed mode is wrong. The pinned kernel's DWC3 driver explicitly supports fixed peripheral mode. Radxa's [ZERO 3 documentation](https://docs.radxa.com/en/zero/zero3) specifies **5 V / 2 A** power on the OTG USB-C port. A Mac connection and blinking LED do not establish that budget or prove a stable boot; use a standards-compliant powered USB-C data path when comparing power behavior, without improvised dual-power wiring.

## Observed board evidence

In the first board capture, `fcc00000.usb` existed but `UDC=` was empty, VID/PID were `0x0000` and both HID gadget nodes were absent. `STARTUP.TXT` incorrectly said `bridge-gadget: already bound`: ConfigFS reports a nonzero attribute inode size even for an empty `UDC` value, so the old `[ -s "$G/UDC" ]` test returned before writing descriptors or binding. The gadget script now tests the attribute's actual string. Dmesg also showed the SteelSeries source keyboard enumerating at **Full-Speed** on the independent `fd000000.usb` xHCI host.

The later user-supplied snapshot confirms the ConfigFS binding fix: `fcc00000.usb` is `configured`, `current_speed=high-speed`, VID/PID `d86a:1000`, both HID functions linked and both `/dev/hidg*` nodes present. Its `STARTUP.TXT` then stops at `bridge-rt-policy: missing verified host/gadget IRQ (host=0 gadget=1)`, so **bridge-daemon never starts** despite correct macOS USB enumeration. Gadget IRQ 28 (`dwc3`) was effectively placed on CPU3; host IRQ 29 (`xhci-hcd:usb1`) remained undiscovered. The revised policy uses the unique live xHCI IRQ label as a fallback, verified against that exact `/proc/interrupts` capture. Gadget High-Speed does not change the source keyboard's observed Full-Speed negotiation. Actual report forwarding and latency must be checked with a new hardware run.

This headless profile also sets the onboard WLAN SDIO1 and Bluetooth UART1 nodes to `disabled` (and disables their kernel stacks); neither is needed for the USB bridge. The separate UART2 serial console and removable storage buses remain enabled.
