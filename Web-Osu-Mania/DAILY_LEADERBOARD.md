# versu! Forest challenge

## Source of truth

The shared Sui `competition::Challenge<CircleUSDC>` vault and `registry::Registry` are authoritative. One Forest of Clock challenge registers **Easy and Hard as different GKR charts** and opens a six-hour scoring period when the Challenge creation transaction executes. The chain Clock fixes `started_at_ms`, `score_deadline_ms = started_at_ms + 21,600,000`, and the subsequent immutable claim deadline. The browser must never infer the deadline from a local calendar date. `registry::Session` accepts a score only after the registered Bridge device signature and Sui-native GKR proof pass. `competition::record_score` accepts only a consumed paid session bound to the original wallet, chart, device and challenge. Each wallet keeps its best verified score separately for Easy and Hard; a score from one chart cannot appear on the other chart's standings.

## Credits and prize pool

One payment of **1,000,000 base units of Circle's six-decimal testnet USDC** buys three nontransferable play credits for that wallet. Credits are shared across Easy and Hard; starting either chart spends one credit atomically with creation of its paid session. A closed tab, failed score, or interrupted run does not return a credit or resume a game. Additional payments add three credits to the same wallet. World ID is not required to buy or play. All purchases enter **one pot**: 30% belongs to Easy and 70% to Hard, regardless of which chart the purchaser selected.

## Claiming and settlement

1. Both difficulties stop accepting paid starts and scores at the same six-hour on-chain deadline. Only Bridge-signed, GKR-verified paid scores rank; a local visual score never ranks.
2. During the fixed claim window, a scored wallet selects **one** difficulty. The World ID v4 Proof of Human verification service checks a challenge-scoped nullifier and that wallet's signed authorization before using the challenge's `IdentityCap` to register the claim. One person may claim one wallet and one difficulty per challenge. A later switch is rejected. Wallets that do not claim may still appear in public score history but receive no prize.
3. After the claim window, either wallet can call `settle`. Each difficulty pays its five highest eligible verified humans **40% / 20% / 20% / 10% / 10% of that difficulty's slice**. Recorded score breaks ties by earlier on-chain record order; claim arrival order does not set rank. Payout goes directly to the bound wallets, not an operator-selected recipient.
4. Missing positions are not redistributed to winners. `refund` returns the remaining balance to purchasers pro rata by purchase count, with final-claim rounding handled on-chain. Historical challenges remain accessible for claim/refund without a controller. The claim window prevents an early payment from being displaced by a later higher score.

## Wallet and hardware flow

Opening standings or switching Easy/Hard does not download an archive. **Practice demo** loads only the 5 KB `daily-demo.osz` after its explicit action; it neither spends a credit nor creates a ranked score. A paid run first loads the 18 MB `forest.osz` on demand, checks both registered source hashes and the selected on-chain chart, then connects the Sui wallet and BridgeOS device, checks device event capacity and the chain's remaining time, buys three shared plays with test USDC if needed, adjusts speed/keys, spends one credit at start, and submits the Bridge-signed trace for a native GKR score. Only those hardware-signed scores enter Easy or Hard standings. After the shared six-hour cutoff, one World ID-verified claim per person may receive a chart's ranked payout. The current development board's 260-point SRS bank exposes only 65 events, insufficient to finish either Forest difficulty; replace it before charging players.

With `VITE_WALLETCONNECT_PROJECT_ID`, the official Mysten WalletConnect Wallet Standard adapter adds a **phone pairing QR** to Sui wallet selection. After pairing, the same desktop-built `buy_plays` PTB is approved on a compatible phone wallet and confirmed on Sui; the QR is *not* itself a payment. Slush/Payment Kit `sui:pay` QR is a plain transfer and is intentionally **not used** because it would not atomically grant 3 credits. A compatible mobile Sui wallet's real PTB approval is still required for a complete phone test.

## Operator configuration

The testnet deployer is `scoring/gkr-scoring-sui/scripts/deploy_forest_challenge.mjs`. Run `--prepare --srs <local-SRS> --out <private-output-dir>` with the funded Sui CLI organizer first: it publishes the native package, creates the shared Registry, and registers both Forest charts, but **does not start the six-hour clock**. Verify confirmed Easy/Hard registration transaction IDs and public source/chart hashes in `deployment.json`. Run `--activate --out <same-dir> --round-date YYYY-MM-DD --device-pubkey 0x<actual-compressed-33-byte-key> --bitstream-hash 0x<actual-32-byte-image-hash> --identity-attestor 0x<service-wallet>` only when the controller, proof server, test USDC, World ID service and players are ready. Activation checks the earlier deployment before registering the real device and creating one `Challenge<CircleUSDC>`; that transaction starts the six-hour clock. The bundled `dev-srs-24.bin` is insecure: explicitly labeled testnet demo only, never real-money deployment.

Copy `deployment.json`'s browser configuration to public `VITE_SUI_*` settings, including **both** chart hashes and the one Challenge ID. `.env.example` lists Circle's native six-decimal testnet USDC type; the site bundles `/beatmaps/forest.osz` for paid runs and `/beatmaps/daily-demo.osz` for free practice. A provisional `VITE_SUI_PROOF_BUFFER_SECONDS=900` reserves time after the measured 139-second Forest chart; replace this buffer using actual Bridge capture, GKR proof and Sui confirmation timings before activation. If deployment or a required dependency is missing, the browser fails closed rather than showing fabricated balances or ranks.

Cloudflare Worker secrets/bindings: a real D1 `WORLD_ID_DB` with `migrations/0001_world_identity.sql`; World `app_id`, `rp_id`, claim action `versu-prize-claim`, RP signing key and environment; Sui network/RPC, attestor private key, package/coin type and **`SUI_IDENTITY_CHALLENGES` keyed by actual Challenge ID** with its `IdentityCap`; authenticated HTTPS `SUI_SCORING_ORIGIN` and server-only `SUI_SCORING_API_TOKEN`. Keep secrets out of `VITE_`. World staging simulator proofs cannot authorize real-world payouts.

The Sui proof server (`scoring/crates/prove-server-sui/`) verifies Bridge-signed GET_RESULT/GET_TRACE bytes and returns a mode-3 Sui transaction plan. Large traces are staged across wallet-signed Sui transactions; mode 3 rejects captures beyond its roughly 7,000-event TraceUpload bound. Provision a bank of sufficient capacity on the **actual** board; the existing 65-event development board cannot finish either Forest chart. Production requires trusted SRS and secure signer firmware, not the bundled development setup.
